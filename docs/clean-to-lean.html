Clean to Lean

Read Clean syntax in terms of Lean binders, terms, declarations, and elaboration. Each mapping records its status so that proposed syntax cannot be mistaken for a compiler feature.

The Lean panels are readable equivalents or explicitly labelled sketches, not canonical kernel-expression dumps. Snippets marked as fragments assume the surrounding parameters and explicitly imported mathematical vocabulary. The compiler’s exact unique-target obligation is stronger than these explanatory displays.

Results are proposition definitions

Implemented

A Clean result declares its statement. It does not introduce a proof, axiom, or Lean theorem.

Clean

Import "../library/linear_algebra.clean"
Import "../library/sources.clean"

Result determinant transpose:
  Attribution: mathlib; Matrix.det_transpose
  Let n: Natural
  Let A: Matrix(n,n,Complex)
  Conclude: det(transpose(A)) = det(A)

Lean

def determinant_transpose : Prop :=
  ∀ (n : ℕ) (A : Matrix (Fin n) (Fin n) ℂ),
    A.transpose.det = A.det

The source imports are concrete repository modules. English result titles generate Lean identifiers with underscores. The current backend places results in CleanStatements and calls generated notation wrappers; the right panel expands those wrappers for readability. A separate Lean proof must inhabit the resulting proposition.

Typed Let introduces parameters

Implemented

Inside a result, typed Let becomes universal quantification. Inside a definition signature, it supplies function parameters.

Clean

Let n: Natural
Let x be a complex n-vector
Let A, S: Matrix(n,n,Complex)

Lean

∀ (n : ℕ)
  (x : Fin n → ℂ)
  (A S : Matrix (Fin n) (Fin n) ℂ),
  ...

Let x: Vector(n,Complex) and the prose form have the same binding role. These are fragments of an enclosing statement. Type names and prose phrases come from explicit modules, not a universal built-in mathematical vocabulary.

Value Let introduces a local definition

Implemented

A value-defining Let is a Lean let, not a new arbitrary parameter.

Clean

Let y = inverse(S)*x
Conclude: y ≠ 0

Lean

let y : Fin n → ℂ := S⁻¹ *ᵥ x
y ≠ 0

Assume n, S, x were already bound. Later clauses can depend on y. The prototype also accepts local Define y = .... Let x = Vector(n,Complex) is rejected; type naming is a separate declaration.

Assume introduces a proof parameter

Implemented

An assumption contributes an implication or dependent proof binder to the generated proposition.

Clean

Assume nonzero: x ≠ 0
Assume eigenpair: A*x = μ*x
Conclude: x ≠ 0 and A*x = μ*x

Lean

∀ (nonzero : x ≠ 0)
  (eigenpair : A *ᵥ x = μ • x),
  x ≠ 0 ∧ A *ᵥ x = μ • x

These are statement fragments under previously introduced parameters. The next-language draft gives assumption labels a separate namespace; they are not proposition-valued variables. The prototype has known debt in that distinction. English labels with spaces are a draft feature, not generally implemented.

Mathematical operators resolve to typed operations

Implemented

The same printed mathematical operator can select different typed Lean operations. The current prototype supports a restricted set.

Clean

A*B
A*x
μ*x
inverse(S)
P and Q

Lean

A * B        -- matrix multiplication
A *ᵥ x       -- matrix-vector multiplication
μ • x        -- scalar action
S⁻¹          -- matrix inverse
P ∧ Q

Assume compatible complex matrix, vector, and scalar types. These lines illustrate separate expressions. The target architecture requires module-declared operator meanings and unique elaboration; the prototype still has name-based dispatch. It is not yet a conforming general overload system.

Contexts project into explicit binders

Implemented

Contexts share source declarations; exported result propositions still carry their required parameters and every inherited assumption.

Clean

Context matrices:
  Let n: Natural
  Let A, B: Matrix(n,n,Complex)
  Result determinant transpose:
    Attribution: mathlib; Matrix.det_transpose
    Conclude: det(transpose(A)) = det(A)

Lean

def determinant_transpose : Prop :=
  ∀ (n : ℕ) (A : Matrix (Fin n) (Fin n) ℂ),
    A.transpose.det = A.det

The unused B is omitted by the specified dependency projection. This resembles section generalization but is not implemented as an unqualified translation to Lean section. LaTeX either expands the context or explicitly cites it.

Type declarations name Lean types

Implemented

Type constructors, aliases, and prose phrases are declared in Clean modules.

Clean

Type VertexSet(n: Natural):
  Means: Finset (Fin n)
  Render latex: \mathcal{{P}}(\operatorname{{Fin}}({n}))

Let S: VertexSet(n)

Lean

-- Declared type meaning:
Finset (Fin n)

-- In an enclosing result:
∀ (S : Finset (Fin n)), ...

Means is a Lean expression; the rendering template is not. The current backend checks generated type wrappers but still substitutes some types textually. Structural dependent-type applications are required by the target spec; the nested matrix-of-functions case remains an acceptance obligation.

Current Notation is a typed Lean adapter

Implemented

The existing notation declaration supplies a callable Clean name, a checked Lean body, and presentation metadata.

Clean

Notation det(A):
  Let n: Natural
  Let A: Matrix(n,n,Complex)
  Returns: Complex
  Means: Matrix.det A
  Render latex: \det({A})

Lean

noncomputable def cleanDet {n : ℕ}
    (A : Matrix (Fin n) (Fin n) ℂ) : ℂ :=
  Matrix.det A

cleanDet is an explanatory wrapper name; the prototype generates a hashed identifier. The omitted header parameter n is inferred from A. This is not automatically a Lean notation declaration, and current Clean notation cannot bind a summation variable.

Define with Equals authors a definition in Clean

Accepted design

The common definition form has exactly one implementation field. Equals contains a Clean expression.

Clean

Define doubled(x):
  Returns: Real
  Let x: Real
  Equals:
    x + x

Lean

def doubled (x : ℝ) : ℝ :=
  x + x

Top-level Define is accepted design, not implemented. Nonparameter fields may be reordered; parameter declarations keep their relative order. The return type and implementation see the complete parameter scope. Explicit imports must supply Real and addition. The right panel is the intended readable target, not an existing compiler output.

Define with From Lean imports an implementation

Accepted design

From Lean elaborates a Lean expression against the same signature used by an authored Clean definition.

Clean

Import Lean CleanPapers.Definitions

Define magnetic matrix(A, q):
  Let n: Natural
  Let A: Matrix(n,n,Real)
  Let q: Real
  From Lean:
    CleanPapers.magneticMatrix A q
  Returns: Matrix(n,n,Complex)

Lean

noncomputable def magnetic_matrix {n : ℕ}
    (A : Matrix (Fin n) (Fin n) ℝ)
    (q : ℝ) : Matrix (Fin n) (Fin n) ℂ :=
  CleanPapers.magneticMatrix A q

The Clean type names require separate explicit Clean imports. A checked adapter can fix parameters or wrap representations; it is not restricted to an alias. Equals and From Lean are mutually exclusive. Generated naming and inference must satisfy the unique-target contract.

Binding notation constructs a lambda

Proposed

A proposed summation form introduces a local variable and supplies a scoped body to a finite sum.

Clean

sum(v in S; degree(G,v))

Lean

Finset.sum S (fun v => degree G v)

-- Familiar Lean notation:
∑ v ∈ S, degree G v

The intended correspondence is domain plus lambda. The semicolon spelling and binding-aware Notation declaration language are proposals, not accepted grammar or implemented features. The declaration must specify the domain, element type, body type, binder scope, and exact Lean construction. Hygiene is required; textual substitution is not a translation rule.

Multiple binders expand in source order

Proposed

The proposed multi-binder sum expands to nested sums. An earlier binder is visible in later domains and the final body.

Clean

sum(u in S, v in complement(G,S);
  adjacency(G,u,v))

Lean

Finset.sum S (fun u =>
  Finset.sum Sᶜ (fun v => adjacency G u v))

For the displayed graph example, both variables range over Fin n; complement is relative to that finite vertex universe. A binder is not visible in its own domain or outside the expression. These are proposed binding rules that still need the full grammar and acceptance fixtures.

Constrained minimum has two scoped bodies

Proposed

A predicate and an objective each use the bound variable. Empty-domain behavior is part of the mathematical definition, not an inference heuristic.

Clean

minimum(S in vertex subsets(G);
  satisfying:
    admissible(G,S)
  of:
    cut conductance(G,S))

Lean

-- Schematic signature, NOT an existing Lean constant:
minimumOperation domain
  (fun S => admissible G S)
  (fun S => cutConductance G S)

No unique translation has been accepted yet: specify the finite minimum construction, any nonemptiness evidence or optional result, and the empty-domain policy first. Ordinary conductance(G) and mu conductance(G,μ) are distinct definitions. The current paper module’s parameterized CleanPapers.conductance implements the size-constrained quantity; it is not the final naming model.

Imports have distinct semantic roles

Accepted design

Import forms exist in the prototype. Their accepted interleaved, sequential placement is not yet implemented.

Clean

Import "graphs.clean"
Import Lean Mathlib.Data.Finset.Basic
Import BibTeX "references.bib"

# Further imports may follow earlier
# top-level definitions in the target design.

Lean

-- Clean module: extend the Clean environment.
-- Lean module: make imported Lean declarations available.
-- BibTeX: load attribution metadata only.

-- The Lean backend arranges required Lean imports
-- in its output prelude.

An import affects only subsequent Clean module items. Hoisting required imports in emitted Lean must not retroactively alter earlier Clean resolution: earlier references retain resolved identities. No one-for-one translation of interleaved source imports to Lean imports is implied. Current Clean modules still impose a pre-result prelude and have scope migration debt.

Attribution and rendering are metadata

Implemented

Provenance and presentation accompany a declaration without becoming logical assumptions.

Clean

Import BibTeX "references.bib"

Attribution: stewart2001; Theorem 1.10; adapted

Render latex: M({A},{q})

Lean

-- Attribution is emitted in documentation / metadata.
-- Rendering is used by the LaTeX backend.
-- Neither changes the Lean proposition or term.

The last two lines illustrate fields in their respective containing declarations, not one complete block. Bibliographic citation keys become source keys. BibTeX parsing is optional (.[bibtex]); crossref/xdata inheritance is currently rejected. Imports and source declarations do not establish a theorem’s truth.

Layout determines scope before mathematical meaning

Accepted design

At least two spaces open a block; siblings align; tabs are forbidden. Inline expression continuation depends on whether the expression is incomplete.

Clean

Let count = n!
Let total = count +
  extra

Equals:
  f(x) + g(x)

Lean

-- Intended structure, assuming the displayed operations:
let count := Nat.factorial n
let total := count + extra
...

-- Equals owns one Clean expression body.
-- From Lean would own a Lean expression body instead.

Flexible indentation and a heuristic continuation implementation exist. Full parser-state continuation, postfix notation, and lexical-mode isolation are target requirements; known prototype deviations remain. The snippets are separate fragments. A postfix application can be complete, whereas an infix operator still requires a right operand.

The acceptance contract

For a fixed source and explicit, pinned environment, accepted input must have one parse and one fully elaborated Lean target and type. Inferred coercions, instance arguments, universe instantiations, and proof arguments count. A term that merely compiles is insufficient.

Distinct parses are syntax ambiguity; distinct permitted targets are semantic ambiguity. Resource exhaustion is incomplete analysis, not a successful choice. See the normative acceptance requirements and pending acceptance cases. The prototype is not certified as conforming.
